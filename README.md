# Moda Interact Background

Background processing, checkout recovery workflows and AI commerce agent for **Moda Interact**.

This service handles asynchronous work generated by the Moda Interact Shopify application and WhatsApp integration. It consumes jobs from BullMQ, persists workflow and conversation state in PostgreSQL, interacts with Shopify, and runs the commerce agent.

                        │

Redis/BullMQ is used for asynchronous execution and PostgreSQL remains the durable source of truth for commercial workflow state and conversation history.

## Responsibilities

The background service currently handles:

- Shopify checkout events
- Shopify order events
- checkout recovery lifecycle management
- customer resolution
- WhatsApp conversation persistence
- inbound and outbound message persistence
- BullMQ retries and failure handling
- conversation state/version tracking
- AI commerce agent execution
- Shopify product search through agent tools
- Shopify access-token retrieval and refresh
- message correlation using provider message IDs

## Checkout Recovery Flow

A Shopify checkout event is received by the main Moda Interact Shopify application and added to BullMQ.

```text
Shopify checkout
      │
      ▼
CHECKOUTS_CREATE webhook
      │
      ▼
moda-interact
      │
      ▼
checkout-events queue
      │
      ▼
Checkout Worker
      │
      ▼
CheckoutRecoveryService
      │
      ├── resolve/create Customer
      │
      ├── create CheckoutRecovery
      │
      ├── create Conversation
      │
      ├── persist outbound message
      │
      └── send recovery message
      │
      ▼
PostgreSQL
```

Checkout recovery has an explicit lifecycle:

```text
DETECTED
   │
   ▼
MESSAGE_SENT
   │
   ▼
ENGAGED
   │
   ├──────────► COMPLETED
   │
   ├──────────► EXPIRED
   │
   └──────────► CANCELLED
```

The recovery lifecycle is stored independently from the LLM conversation.

This means the application does not rely on the language model to determine the current commercial state of a checkout.

# WhatsApp Inbound Message Flow

The WhatsApp webhook is responsible for processing inbound customer messages and determining which `CheckoutRecovery`, if any, the customer is responding to.

A customer may have multiple active abandoned checkouts, so an inbound WhatsApp message cannot always be associated with a recovery using the customer's phone number alone.

The resolution flow therefore uses deterministic WhatsApp context where available and falls back to the `CommerceAgent` when the message is ambiguous.

## Flow

```text
WhatsApp Webhook
      │
      ▼
Receive inbound message
      │
      ▼
Identify customer / conversation
      │
      ▼
Create inbound Message
      │
      ▼
Does the WhatsApp message contain context.id?
      │
   ┌──┴───┐
   │      │
  YES     NO
   │      │
   ▼      ▼
Lookup original             Load all active
outbound Message            CheckoutRecoveries
using context.id            for the customer
   │                           │
   ▼                           ▼
Find associated            Provide the customer's
CheckoutRecovery           message and recovery
   │                       line items to CommerceAgent
   │                           │
   ▼                           ▼
Recovery resolved          CommerceAgent determines
deterministically          the most likely recovery
                               │
                          ┌────┴─────┐
                          │          │
                       MATCH      AMBIGUOUS
                          │          │
                          ▼          ▼
                    Return recovery  Ask customer
                    identifier       for clarification
```

## Commerce Agent

The commerce agent uses Groq through the Vercel AI SDK.

When a customer sends a message, the agent context is rebuilt from the latest persisted application state.

```text
Customer message
      │
      ▼
Conversation
      │
      ├── current CheckoutRecovery
      ├── Customer
      ├── conversation summary
      └── recent messages
      │
      ▼
Commerce Agent
      │
      ├── reasoning
      │
      └── Shopify tools
              │
              ▼
        Shopify Admin API
```

The LLM is therefore treated as a reasoning layer rather than the source of truth for the workflow.

The agent can call tools such as product search to retrieve current Shopify data instead of inventing product, pricing or availability information.

## Conversation Processing

Conversation and message state is persisted in PostgreSQL.

Each inbound message has a provider message ID which is used for deduplication and correlation.

The conversation also tracks:

```text
inboundVersion
lastProcessedVersion
lastInboundAt
lastMessageAt
summary
```

Versioning allows the worker to detect when newer inbound messages have arrived while an agent response is being generated.

This helps prevent stale AI responses from being sent when multiple messages arrive close together.

## Idempotency

Webhook delivery and background processing are designed to be idempotent.

Checkout jobs use a deterministic identifier based on:

```text
shop + checkoutToken
```

This prevents duplicate Shopify webhook deliveries from creating multiple logical recovery jobs.

Database constraints provide additional protection around:

```text
(shop, checkoutToken)

(shop, phone)

(shop, shopifyCustomerId)

providerMessageId
```

BullMQ retries are used for processing failures rather than generating new job identifiers.

### Billable action keys

Each billable action should use a deterministic `idempotencyKey`. The key
identifies the action being recorded, so retries produce one usage event rather
than charging the same action multiple times.

Use a different key namespace for each billable action:

```text
checkout-recovery:${recovery.id}
conversation:${conversation.id}
agent-message:${message.id}
whatsapp-message:${message.id}
```

The `UsageService.record` method accepts the following input:

```typescript
interface RecordUsageInput {
      shopId: string;
      metric: UsageMetric;
      quantity: number;
      idempotencyKey: string;
      sourceType?: string;
      sourceId?: string;
}
```

For example:

```typescript
await usageService.record({
      shopId,
      metric: "monthly_recoveries",
      quantity: 1,
      idempotencyKey: `checkout-recovery:${recovery.id}`,
      sourceType: "CheckoutRecovery",
      sourceId: recovery.id,
});
```

## Queues

The service currently consumes BullMQ queues including:

```text
checkout-events
order-events
whatsapp-events
```

The queue layer allows webhook ingestion and long-running work to scale independently.

For example, additional worker instances can be added without increasing the number of Shopify webhook servers.

## Local Development

Clone the repository including its database submodule:

```bash
git clone --recurse-submodules \
  https://github.com/kodjobaah/moda-interact-background.git

cd moda-interact-background
```

If the repository was cloned without submodules:

```bash
git submodule update --init --recursive
```

Install dependencies:

```bash
npm install
```

Generate the Prisma Client:

```bash
npm run prisma:generate
```

Build the project:

```bash
npm run build
```

Start the worker service:

```bash
npm start
```

## Design Principles

Moda Interact is built around a few core architectural principles:

1. **Persist business state outside the LLM**  
   PostgreSQL is the source of truth for checkout recovery and conversation state.

2. **Separate commercial workflow from conversation history**  
   `CheckoutRecovery` controls the commercial lifecycle while `Conversation` represents interaction context.

3. **Keep webhook handlers lightweight**  
   Long-running and retryable operations are moved onto BullMQ workers.

4. **Make external integrations replaceable**  
   Shopify, Groq and WhatsApp are accessed through defined service/provider boundaries.

5. **Design processing to be idempotent**  
   Duplicate webhook deliveries and message events should not create duplicate business actions.

6. **Scale workers independently**  
   Queue consumers can be horizontally scaled according to workload without redesigning the domain model.

7. **Avoid premature infrastructure complexity**  
   PostgreSQL and Redis provide sufficient scalability for the current system while preserving clear future boundaries for higher-volume workloads.
