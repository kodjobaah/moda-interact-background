# ARCH-049-BACKGROUND-002 — durable ShopBrand JSONB orchestration

- **Database acceptance:** The short `commerce."ShopBrand"` row-lock transaction is the only source of truth. Source events produce generation-qualified `PENDING`, claims acquire expiring per-role leases, and completion/failure compare owner, generation, fingerprint, URL and unexpired lease before updating JSONB. Image downloads and R2 requests occur strictly outside these transactions. Concurrent first observations upsert by `shopId`; independent role edits preserve sibling JSON keys.
- **Source updater:** Import `ShopBrandMediaRepository.observeSource({ shopId, role, sourceUrl, sourceReference, sourceFingerprint, observedAt })`. When upstream fingerprint is null, deterministically derive `sha256:` plus SHA-256 of `JSON.stringify([sourceUrl, sourceReference])` UTF-8. An older or equal `observedAt` cannot replace the accepted observation, even if its URL differs. A newer, identical observation only advances observedAt. New/removed source increments generation and resets role work, preserving former ready only for audit, never for delivery.
- **Media statuses:** `MISSING`, `PENDING`, `PROCESSING`, `FAILED`, `READY`. Initial claims increment `work.attempts`, with retry times 1m/5m/30m/2h/24h; no sixth claim for a generation. Expired fifth-attempt leases become terminal `FAILED/LEASE_EXHAUSTED`. Permanent errors have no retryAt. The retry/failure code is a bounded category, never a provider message.
- **READY refresh:** Seven days after lastCheckedAt/verifiedAt, Background may claim `work.refresh` separately while leaving `work.status=READY` and the last-current-generation `ready` unchanged. On verified success, CAS swaps the digest/key (the same digest retains the same immutable object key). A transient refresh failure uses separate `work.refresh` attempts/failureCode/retryAfter without suppressing the existing asset. After a permanent error or exhausted attempt budget, a fresh recheck cycle becomes eligible seven days later. Changed source generation invalidates the old ready immediately.
- **Scan:** A background five-minute scanner runs inside the already deployed Recovery worker. It keyset-pages the unique ShopBrand.shopId index (50 rows/page, at most 500 rows/tick); at most 20 media operations per tick with a two-operation maximum concurrent process limit. The in-memory pagination cursor advances after inspected shops and wraps at the end. Replicas may scan overlapping pages; claims arbitrate via PostgreSQL row locks. No new enum lease, durable queue, R2 bucket, webhook or Gateway deployment is needed. The PENDING commit survives lost wakes and restarts.
- **Observability:** All runtime error-path events use `@modainteract/moda-interact-shared/logging` and explicit bounded shop/role/generation/reason-code metadata, never credentials, untrusted source URLs, raw provider errors or customer payloads. Retryable PostgreSQL contention is logged at `warn` on **each** intercepted exception; final transaction failure is logged at `error` and rethrown. Scan-page and per-row exceptions are logged before fail-fast/isolated continuation; each per-claim completion exception is logged with its own safe claim context before the aggregate error reaches the scheduler. The optional local wake logs failures and propagates them. The scheduler logs sweep and startup failures. BG001 processing exceptions are logged and durably recorded as retryable/terminal role failures; stale error-record CAS is visible at `warn`. Expected stale-claim rejection remains a normal outcome, not an exception. Never use empty `catch` branches to discard exceptions or pass raw untrusted `Error.message` to the logger. No duplicate generic HTTP/worker telemetry.
- **Delivery:** `currentReady` verifies same-generation source fingerprint, JPEG/PNG format, dimensions, size, immutable key syntax and output digest. Consumers **must additionally verify** active trusted HTTPS public origin and permitted role/key when forming WhatsApp media bindings; this task is not a send-time renderer. A READY image does not imply a Meta template has an approved IMAGE header.
- **Validation:** `npm test -- tests/unit/services/shop-brand-media-orchestration`; `node scripts/test-integration.mjs tests/integration/shop-brand-media-orchestration.integration.test.ts` with disposable PostgreSQL; `npm run lint`; `npm run build`; `git diff --check`. Validate dedicated launcher-resolved parent/implementation worktrees and task claim before accepting.
