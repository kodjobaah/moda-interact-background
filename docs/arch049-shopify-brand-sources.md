# ARCH-049-BACKGROUND-003 — Shopify Brand API source synchronisation

- **Provider:** Background's existing offline Shopify token retrieval and Shopify Admin GraphQL `2026-07`; `shop { name brand { logo(assetType: DEFAULT_LOGO) squareLogo: logo(assetType: SQUARE_LOGO) coverImage } }`. `squareLogo` is only a GraphQL alias for `logo(assetType:SQUARE_LOGO)` (not an Admin `BrandingBrand.squareLogo` field). All image sources read `originalSrc`, `id`, `mediaImageId`, `width`, `height`. Admin branding does not return alt text, so the corresponding optional ShopBrand alt fields remain null. Independent square absent -> `squareLogoUrl=null` but SQUARE_LOGO role observes the main logo as an explicit derived fallback.
- **Authentication:** Scan only `Shop.platform=SHOPIFY`, `Shop.status=ACTIVE`; require its offline `Session.scope` to contain `read_brand` before requesting a token. Verify the DB shop's domain under the source-claim transaction; send credentials only to validated `*.myshopify.com` hosts. Missing grant/auth/session, HTTP/GraphQL errors, 429, network errors and invalid/incomplete responses **never erase the last source**. No Storefront, scraping, WooCommerce or R2 calls.
- **Durability:** The existing BG002 `ShopBrandMediaRepository` owns all row-locked source modifications. A successful provider response atomically updates the original ShopBrand columns and all three `whatsAppMedia.roles` using BG002's `updateObservedSource`; changed/removal sources advance the generation, unchanged URLs/reference preserve it. Concurrent BG002 media claim/complete preserves independent JSON keys. Success writes `fetchedAt`, while `lastRefreshedAt` remains Prisma-managed (also changes during media processing).
- **Scheduler metadata:** Adds a bounded optional `whatsAppMedia.shopifySourceSync` field within **the same version-1 JSONB document** (no database schema change). It contains `lastSuccessfulAt`, `nextDueAt`, `lastAttemptAt`, `attempts`, `failureCode`, `leaseOwner`, `leaseUntil`. BG002 JSON role updates explicitly preserve this top-level field. A short row lock grants a two-minute lease; stale/expired lease owners cannot change sources; success sets nextDueAt to +24 hours, failures persist an allowlisted reason code and retry at 1m / 5m / 30m / 2h / 24h or no sooner than a bounded Shopify Retry-After. No provider call occurs under the database lock. An unobserved Shop creates its ShopBrand row at claim time (never fabricates brand sources).
- **Bounded scan:** The existing Recovery worker starts a separate five-minute source scheduler, keyset scanning active Shopify shops in pages of 50, at most 500 shops / 20 source claims / two concurrent reads per tick. A single shop cannot monopolise a scan, and the cursor wraps after reaching the end. Expired leases and failed provider calls are reconsidered after their durable nextDue; no BullMQ, new worker service, or additional database table/column is required.
- **Logging:** `@modainteract/moda-interact-shared/logging`, with shop ID and bounded error/status codes. Never include raw source URLs, GraphQL error messages, tokens or response payloads. Per-shop failures and persistence exceptions are logged distinctly. The latter reject the sweep; a lease is reclaimable if the DB write fails.
- **Local validation:** `npm ci` (if required), `npm run prisma:generate`, `npm run test:arch049-shopify-brand:unit`, `npm run test:arch049-shopify-brand:postgres` (disposable Docker PostgreSQL), `npm run lint`, `npm run build`, `git diff --check`. Test a real store that has approved `read_brand` and verify the exact GraphQL version before enabling production sends. Do not claim the Shopify grant is active merely because the app TOML requests it.
- **Deployment:** Roll out database migration and Admin raw-SQL update before new Background worker. No additional app scope change here; ARCH-049-SHOPIFY-001 owns Shopify reauthorisation. The existing BG002 revalidation scanner remains independent of this daily Shopify source sync.
