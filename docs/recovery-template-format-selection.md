# Recovery template format selection

The platform default table is provisioning configuration, not send authority. Background continues to read the merchant's enabled, approved `WhatsAppTemplateVariant` rows, frozen Meta registrations and current common-layout evidence. Neither Shopify nor WooCommerce requires a branding record for the TEXT baseline. There is no new table, queue, provider read or default lookup in the recovery send path.

- Automated initial and follow-up preparation prefers an independently eligible IMAGE assignment. A missing optional IMAGE assignment selects TEXT normally. An unavailable verified header derivative selects an independently eligible TEXT assignment for the same recovery purpose using the existing language/greeting policy; it does not change an already verified offer. Record the rejected IMAGE and selected TEXT variant IDs (or both failure codes), without customer text, URLs or secrets. A failed mandatory BODY binding, stale layout, corrupt immutable projection, unexpected infrastructure exception or final permit denial is not an instruction to strip a header or send unapproved content.
- The existing optional-enrichment no-offer fallback explicitly selects TEXT. This never changes an admitted or uncertain provider send. An ordinary no-offer recovery still prefers an eligible ready IMAGE.
- Merchant-initiated follow-up resolves the exact persisted provider template name/language through the current tenant/purpose/format catalogue. Selection does not override language, greeting, offer or approval checks; an explicitly chosen IMAGE that is not ready is refused rather than silently sending a different template. Legacy templates still require their approved checkout CTA button. A verified common-layout template can instead carry the bound checkout URL in its BODY; the existing final permit validates the exact current registration, current common layout, recovery URL and provider parameters.
- Existing consent, STOP, moderation, capacity/credits, final registration and provider outcome fences are unchanged. Missing or invalid TEXT assignment remains a configuration/eligibility issue, not permission to send arbitrary WhatsApp text outside the messaging window.

Validation: run `npm run prisma:generate`, `npx tsc --noEmit`, focused recovery-template-preparation, recovery-template-integration and merchant-follow-up tests, and `node scripts/test-integration.mjs tests/integration/recovery-template-formats.integration.test.ts` using disposable PostgreSQL and Redis. The new DB test uses real local assignment/registration reads for a locked Shopify brand source and a WooCommerce merchant without a brand row; R2/network delivery is not part of that test. Full system tests must still exercise actual onboarding, moderation, credit reservation/settlement and provider dispatch for both platforms. The WooCommerce human follow-up catalogue's separate API/plugin presentation contract is unchanged.
